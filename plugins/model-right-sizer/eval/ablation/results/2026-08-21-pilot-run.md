# Layer-ablation study — pilot run, 2026-08-21

First real run of the study designed in [`../DESIGN.md`](../DESIGN.md), executed via
[`../../../skills/model-right-sizer-layer-ablation/SKILL.md`](../../../skills/model-right-sizer-layer-ablation/SKILL.md).
Checked in as a worked example and an honest record of what this pilot scale
can and can't show — not a final verdict on the four layers.

## Scope actually run

- **Composition sweep (Outcome 2 — combination): the full 16-condition × 6-task grid, 96 blueprints, all valid on first or second pass.** Every layer subset from the zero-layer baseline to the shipped `all_four` agent, across all six `benchmark_tasks.json` tasks.
- **Accuracy sweep (real execution): 2 conditions × 2 tasks = 4 real builds**, a small slice of DESIGN.md's already-reduced default (6 conditions × 6 tasks). Composition got the full grid; accuracy did not — that's a deliberate cost tradeoff, named here rather than blurred.
- Isolation (Outcome 1) is read off the same 96-blueprint grid: baseline vs. each of the four single-layer conditions.

## Two limitations discovered *by running this*, not anticipated in the design

Both are real findings from dogfooding the harness, not the citation layers themselves — reported because hiding them would make every other number below look more precise than it is.

### 1. Each condition's six tasks shared one agent session (a within-condition correlation confound)

For the composition sweep, each of the 16 conditions was dispatched as **one** sub-agent handling all six tasks in one session, not six independent sub-agents (a deliberate cost-saving shortcut in this run — the SKILL's own design specifies one dispatch per condition×task cell precisely to avoid this). The result: some swings across tasks within one condition look more like one session's idiosyncratic tendency than six independent draws — e.g. the `ibpo` condition picked `claude-opus-5` in 9 of 16 rows, a rate no other condition came close to, most plausibly one session's persistent preference carried across its own six tasks rather than four independent effects. Treat any single condition's numbers as **n=1 session**, not n=6 independent samples, until re-run with per-cell independent dispatch.

### 2. `token_ceiling` semantics are ambiguous for a high-volume fan-out task, and different runs picked different conventions

`mean_token_ceiling` swung from ~22k to ~340k across conditions in the raw 16-condition table — almost entirely driven by `t1_bulk_classifier` (classify 10,000 items), where different runs' blueprints set `token_ceiling` to anywhere from **200** (read as a per-item budget) to **2,500,000** (read as a total-campaign budget for all 10,000 items) for the identical intent. This is a genuine specification gap in `schemas/blueprint.schema.json` — it doesn't say which convention a fan-out stage's ceiling means — not a citation-layer effect. The isolation table below is reported **both** ways: raw (all 6 tasks) and excluding `t1` (5 tasks), and the `t1`-driven swing should not be read as evidence about any layer.

**Follow-up this pilot surfaces, not yet actioned:** `schemas/blueprint.schema.json` should probably require `budget.token_ceiling` to state its own unit (per-item vs. per-batch/campaign) for any stage that isn't single-shot — filed here as a finding, not fixed in this run.

## Outcome 1 — isolation (baseline vs. each layer alone, + the shipped `all_four`)

Excluding `t1` (5 tasks/condition) — the cleaner comparison per the caveat above:

| mean_confidence | 65.6 | 61.7 | 61.0 | 62.5 | 65.9 | 57.7 |

| mean_efficiency | 57.3 | 41.9 | 49.0 | 46.1 | 54.2 | 48.0 |
| mean_difficulty | 43.0 | 52.2 | 53.3 | 49.0 | 48.2 | 50.4 |

**Two patterns that survive the `t1`/session caveats above, because they're consistent across every layer-bearing condition rather than one outlier:**

- **`query_shaped_rate` is ~2x higher at baseline (0.188) than in every single condition that carries any one of the four layers (0.067–0.083), including `all_four`.** Adding a citation layer — any of the four — correlates with the agent flagging roughly half as many stages as candidates for the deterministic-query-layer lever, in this run. One plausible mechanism: a longer, more numerically-dense system prompt (any of the four sections add real length) shifts attention toward model-tier/effort reasoning and away from the query-layer fork, which lives earlier in the "Levers" list and is unchanged across all 16 variants. This is worth a repeated run with independent per-cell dispatch before treating it as established — it's exactly the kind of side effect an ablation study exists to catch, and it's a plausible one, not a certain one.
- **`mean_difficulty` is higher in every layer-bearing condition (48.2–53.3) than baseline (43.0).** Consistent with each layer's own stated purpose in some form (IBPO and BudgetThinker explicitly reason about difficulty/budget; Token Economics' cost-of-error framing plausibly reads ambiguous/high-stakes tasks as harder) — but again, one session per condition, so this wants a repeat run before being treated as more than suggestive.

### The clearest single finding: speculative decoding's signature task, read qualitatively

For `t4_interactive_latency_sensitive_chat` (the SD-signature task — low concurrency, self-hosted vLLM, latency is the complaint), the **baseline** blueprint's rationale reads:

> "...the biggest lever may be outside the model-tier axis altogether: since the org controls its own vLLM cluster, serving-layer tuning (streaming chunk size, **speculative decoding**, continuous batching at low concurrency, prefix/prompt caching across turns) is likely to move latency more than which tier is picked."
> — primary pick: **Haiku 4.5, effort: none**

Baseline *names* speculative decoding (general pretraining knowledge, not this repo's citation, can surface the term) but only as one item in a list, and still defaults to the traditional lever — downgrade the model tier. The **all_four** blueprint for the identical intent:

> "...the org self-hosts its own inference stack with low concurrency — the textbook precondition for buying back latency via speculative decoding (a small draft model proposing tokens the primary model verifies in parallel) rather than downgrading model tier. Gate: this only helps if the draft model's acceptance rate α exceeds the cost-coefficient c (Corollary 3.9); below that gate, no proposal length helps and the lever should be dropped..."
> — primary pick: **Sonnet 5, effort: medium**

This is the qualitative shift the layer's own design predicts: not a name-drop, but the exact formal gate (Corollary 3.9, α > c) invoked by name, and a primary recommendation that explicitly keeps the stronger model instead of downgrading it. This is the strongest single piece of evidence in this pilot that the speculative-decoding layer changes *what gets recommended*, not just what gets said — one task, one pair of runs, but a clean qualitative signature match to the layer's own stated purpose.

## Outcome 2 — combination (all 16 conditions)

Full table in [`report.json`](report.json) (checked in alongside this file — the actual 96-blueprint composition-metrics dump). Headline read: **the surface is not monotonic** in the number of layers present — e.g. `mean_token_ceiling` (raw, all 6 tasks) is *higher* for several 2- and 3-layer combinations than for either the zero-layer baseline or the all-four condition, before the `t1` caveat is even applied. Whether that's a real interaction (layers partially "canceling out" when combined) or session-to-session noise given the n=1-session-per-condition limitation above is exactly the open question a repeat run with independent per-cell dispatch would answer — this pilot can name the question, not close it.

## What would raise confidence in a repeat run

1. **Independent dispatch per (condition, task) cell** — the single biggest fix; removes the within-session correlation confound entirely.
2. **More than one repetition per cell** — even 3 independent runs per cell would let a real per-layer effect be distinguished from single-run noise, which this n=1-per-cell pilot cannot do.
3. **A `token_ceiling` unit convention fix in `schemas/blueprint.schema.json`** (or at minimum, excluding/normalizing fan-out tasks in the metric) before trusting `mean_token_ceiling` comparisons at all.
4. **Accuracy measurement normalized for agent-dispatch overhead** — see below.

## Accuracy — real execution, 4 cells (`baseline`/`all_four` × `t6`/`t4`)

| condition | task | budgeted_tokens | actual_tokens (harness-reported) | adherence ratio |
|---|---|---:|---:|---:|
| baseline | t6_bounded_wellspecified_fix | 8,000 | 40,842 | 5.11x |
| baseline | t4_interactive_latency_sensitive_chat | 4,000 | 31,452 | 7.86x |
| all_four | t6_bounded_wellspecified_fix | 6,000 | 41,081 | 6.85x |
| all_four | t4_interactive_latency_sensitive_chat | 2,000 | 43,290 | 21.65x |

`accuracy_rate` (the user's brief's own definition — "expected effort stayed within prediction") is **0.0** for both conditions measured. **Do not read this as "the agent's budgets are unreliable."** All four cells were dispatched as a general-purpose Claude Code sub-agent, and `actual_tokens` above is the harness's own reported `subagent_tokens` for that whole dispatch — which includes the sub-agent's system prompt, tool-call schemas, and framework overhead, not just the task-specific reasoning/output the blueprint's `token_ceiling` was almost certainly sized against. A `token_ceiling: 2000` line is estimating a bounded reasoning+output budget for one stage, not a full agent-harness invocation's total footprint; comparing the two directly is an apples-to-oranges measurement bug in *this pilot's accuracy methodology*, discovered by actually running it — exactly what dogfooding is for. **This needs a fixed baseline-overhead subtraction (or a leaner, non-agentic execution harness) before `accuracy_rate` numbers here mean anything about the layers.** Until that's fixed, treat this section as "the mechanism works end-to-end (real budgets in, real usage out, real classification)," not as a verdict on any layer's budget accuracy.

## Bottom line

- The harness works end-to-end: 96/96 blueprints generated and schema-valid, 4/4 real builds executed and classified.
- The single most defensible finding is qualitative, not a metric: the speculative-decoding layer visibly changes the *recommendation itself* (keep the strong tier + use the serving lever, vs. downgrade the tier) on its signature task, with the paper's own formal gate invoked by name.
- Every quantitative aggregate in this pilot carries at least one of two disclosed confounds (within-session correlation; `token_ceiling` unit ambiguity on fan-out tasks) and should be treated as suggestive, not established, until repeated with independent per-cell dispatch and a fixed accuracy-overhead baseline.
- `accuracy_rate` as measured here is not yet meaningful — it needs the overhead-normalization fix named above before it says anything about the layers.
