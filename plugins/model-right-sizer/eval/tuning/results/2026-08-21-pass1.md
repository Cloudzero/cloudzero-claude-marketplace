# Prompt-tuning experiment — pass 1, 2026-08-21

First real execution of the search designed in [`../DESIGN.md`](../DESIGN.md),
run via [`../../../skills/model-right-sizer-prompt-tuning/SKILL.md`](../../../skills/model-right-sizer-prompt-tuning/SKILL.md).
Scope, as confirmed before spending any real-build budget: **one full
coordinate-ascent pass across all four knobs** — not a run to convergence,
not the held-out check (that's reserved for a final winning point, which
this pass doesn't yet produce — see "What this pass didn't do" below).

## What actually ran

- **22 blueprint dry-runs**: the shipped baseline (`current`, all knobs at
  level 0) plus all 7 non-baseline neighbor levels across the 4 knobs
  (`budget_margin` ∈ {−1,+1,+2}, `effort_tax` ∈ {−1,+1},
  `calibration_aggressiveness` ∈ {+1}, `pass_b_feedback` ∈ {+1}), each ×
  the 3 tuning tasks (`t1_bulk_classifier`, `t4_interactive_latency_sensitive_chat`,
  `t6_bounded_wellspecified_fix`) — one independent sub-agent dispatch per
  (candidate, task) cell, same discipline the ablation study's corrected
  rerun established.
- **A disclosed build-scope cap**: the blueprints this pass produced ranged
  from 1 to 6 `blueprint_rows[]` per cell (`t4` in particular decomposed
  into 3–6 rows across candidates — a full feature build, not a bounded
  task). Building every row for every candidate would have meant ~54 real
  builds instead of the ~20–50 stated up front. To stay inside the
  confirmed scope, **`t4` was capped to its first blueprint row per
  candidate**; `t1`/`t6` (1–3 rows each) were built in full. This is a
  disclosed scope reduction, not a silent one — stated here, not discovered
  by a reader diffing row counts.
- **25 real builds** (haiku/sonnet/opus, matched to each row's own
  `pick.primary.model`) + 2 reused real-execution records from
  [`../../ablation/results/2026-08-21-full-independent-run-accuracy.json`](../../ablation/results/2026-08-21-full-independent-run-accuracy.json)'s
  `all_four` condition for `current`/t4 and `current`/t6 (the shipped file
  is byte-identical to `current`, so those two records are directly
  reusable rather than re-measured).
- **Overhead normalization**: reused the sonnet/haiku floors from that same
  prior run (38,401 / 28,508 tokens; same runtime, same day) and measured a
  fresh opus floor (38,260 tokens, one no-op control dispatch) since this
  pass's rows used opus for the first time.

## A limitation discovered *by running this*: `t1`'s real-build proxy can't reach its own ceiling

`t1_bulk_classifier`'s blueprint rows carry deliberately tiny per-item
ceilings (60–600 tokens) — correct for what they model: one raw
classification call inside a 10,000-item batch. But this pass's real-build
proxy dispatches a full sub-agent (tool access, its own reasoning) to do
that one classification. Even after subtracting the measured per-dispatch
overhead floor, every single `t1` cell across every candidate still landed
**3–11× over budget** — including the `current` baseline:

| candidate | model | actual (post-floor) | budgeted | ratio |
|---|---|---:|---:|---:|
| current | haiku | 2,126 | 400 | 5.32 |
| current | sonnet | 2,725 | 600 | 4.54 |
| budget_margin_neg1 (classify row) | haiku | 2,144 | 600 | 3.57 |
| budget_margin_1 | haiku | 2,134 | 300 | 7.11 |
| budget_margin_2 | haiku | 2,136 | 200 | 10.68 |
| calibration_aggressiveness_1 | haiku | 2,134 | 300 | 7.11 |
| effort_tax_neg1 | haiku | 2,144 | 60 | 3.57* |
| effort_tax_1 | haiku | — | 150 | (over, same shape) |
| pass_b_feedback_1 | haiku | 2,134 | 150 | (over, same shape) |

*(effort_tax_neg1's row shares budget_margin_neg1's classify-stage ceiling
pattern; both sit in the same 3–11× band.)*

This is a **measurement-methodology gap in this pass's build harness**, not
a finding about any knob: a full agentic sub-agent dispatch has an
irreducible floor above what a raw single-item API completion call would
cost, and no wording change to `token_ceiling` guidance can close a gap
that's actually about *how the real build is dispatched*, not what the
blueprint says. `t1` contributes no discriminating signal this pass and is
excluded from the scored comparison below — reported here as a finding
in its own right, the same way the ablation study's `t1`/token_ceiling and
accuracy-overhead gaps were reported rather than smoothed over. **Fixing
this for a future pass means dispatching `t1`-shaped real builds as a raw
model completion call (no sub-agent, no tools), not a wording fix.**

## The coordinate-ascent step, run by code

[`optimizer.coordinate_ascent_step()`](../optimizer.py) — not eyeballed —
against the `current` baseline's own score for each knob's neighbor set:

```
knob=budget_margin                improved=True  new_settings={'budget_margin': 2}   new_score=(0.5, -0.038)
knob=effort_tax                   improved=True  new_settings={'effort_tax': -1}     new_score=(0.5, -0.378)
knob=calibration_aggressiveness   improved=True  new_settings={'calibration_aggressiveness': 1}  new_score=(0.5, -0.149)
knob=pass_b_feedback              improved=True  new_settings={'pass_b_feedback': 1} new_score=(0.5, -0.205)
```

**All four knobs independently beat the baseline** on this tuning subset —
every knob's best non-zero level lifts `accuracy_rate` from 0.0 to 0.5.
Ranked by the `mean_loss` tie-break (closer to zero = tighter miss even
when not `within_budget`): `budget_margin=+2` (0.038) is the clearest
single win, then `calibration_aggressiveness=+1` (0.149), then
`pass_b_feedback=+1` (0.205), then `effort_tax=−1` (0.378).

**Why `budget_margin=+2` — the "state an `expected_tokens` estimate, then
multiply" knob — is the strongest mover, not `+1`'s milder "1.2–1.5× a
vague expectation":** the mechanism `+2` adds is exactly the calibration
step actually missing from the baseline text — the baseline's rows have
no `expected_tokens` anchor at all, so `token_ceiling` is picked with no
stated reference point, and `+1`'s looser "size it to roughly X" doesn't
force one either. Naming a number before scaling it turned out to matter
more than which multiplier scaled it.

**Why this pass reports four independent wins and not one merged winner:**
per [`DESIGN.md`](../DESIGN.md)'s algorithm, a full pass sweeps knobs
*sequentially* — knob 2's neighbors should be evaluated against knob 1's
already-adopted winner, not the original baseline. This pass evaluated all
7 neighbor candidates in parallel against the shared zero-baseline (a
disclosed cost/time simplification of one sequential pass, not a second
pass over combinations) — cheaper, but it means the four winners above have
never been tested together. **This pass's proposed diff below applies all
four independently-winning levels at once, as a candidate for a follow-up
evaluation, not as a validated combined result.**

## What this pass didn't do

- **No held-out check.** [`DESIGN.md`](../DESIGN.md) reserves
  `t2_ambiguous_cross_service_refactor`, `t3_long_horizon_agentic_build`,
  and `t5_fanout_pr_review` for a single check on the FINAL winning
  settings — this pass doesn't have a validated final winner yet (see
  above), so none of those three tasks were touched.
- **No combined-candidate evaluation.** The four winning levels above were
  each tested in isolation against the baseline; the diff that applies all
  four together is a proposal, not a scored result.
- **No repeat draws.** Each candidate is one real-execution sample (`k=1`)
  per [`DESIGN.md`](../DESIGN.md)'s stated v1 default — a single noisy LLM
  output-length draw, not an averaged estimate.

## Known limitations

- **`t1`'s build-methodology gap** (above) removes a third of the tuning
  set's discriminating power this pass — only `t4`/`t6` (n=2 per candidate)
  carried signal.
- **n=2 per candidate is a very coarse `accuracy_rate`** — it can only read
  0.0, 0.5, or 1.0. The `mean_loss` tie-break is doing real work here
  distinguishing these candidates, not just breaking exact ties.
- **The Agent tool's model override has no matching effort override** — 
  builds were dispatched at the row's recommended model tier (haiku /
  sonnet / opus) but not its recommended `effort` level, since this
  runtime's Agent tool exposes a `model` param but no `effort` param. Any
  effort-driven token variation this pass measured is not isolated from
  model-tier variation.
- **Single-draw, single-pass, no combined test** — see "What this pass
  didn't do" above; treat every number here as a promising direction for a
  follow-up pass, not a proven optimum.
