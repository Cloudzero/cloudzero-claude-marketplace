# Prompt-tuning pass 2 — and why passes 3–4 are paused, not skipped

**Scope confirmed before spending build budget:** continue the sequential coordinate-ascent
search from [pass 1](2026-08-21-pass1.md)'s combined winners
(`budget_margin=+2, effort_tax=-1, calibration_aggressiveness=+1, pass_b_feedback=+1`), add
the newly-added 5th knob `calibration_decay` (grounded in SelfBudgeter's real α-decay
formula — see `../DESIGN.md`'s "Grounding the 5th knob" section for why this replaced the
original, unsupportable `lambda` framing) at its baseline level, and re-evaluate. Planned
cost: 10 candidate evaluations (1 baseline + 9 neighbors across 5 knobs) × 2 tuning tasks
(t4, t6) × 1 real build per row ≈ 20 real builds, plus 20 Pass A dry-runs.

**What actually happened:** the dry-run stage surfaced a second, independent measurement
breakdown — on top of pass 1's already-known t1 problem — that made the *planned* real-build
count both wrong and, on t4, no longer worth spending. Both are reported here in full rather
than silently worked around.

## Finding 1: t4 now decomposes into 5–7 real-execution rows per candidate, not 1

Every one of pass 1's t4 candidates dry-ran to a single blueprint row. At pass 2's starting
point (`budget_margin=+2` pinned, now combined with the other three pass-1 winners), **every
one of the 10 candidates' t4 dry-runs decomposed into 5–7 rows** — design/architecture,
backend streaming implementation, speculative-decoding evaluation, frontend UI, a benchmark
harness, and a review stage each showed up as its own row, mostly at Sonnet/Opus tiers with
token ceilings from 15,000 to 80,000. This wasn't one outlier candidate: `pass2_current` (6
rows), `budget_margin_neg1` (7 rows), `budget_margin_0` (5 rows), `budget_margin_1` (6 rows),
`effort_tax_0` (7 rows), `effort_tax_1` (8 rows), `calibration_aggressiveness_0` (5 rows),
`calibration_decay_1` (5 rows), `calibration_decay_2` (5 rows), `pass_b_feedback_0` (5 rows)
— every single one.

Real-building all of that would have meant roughly 55 real t4 dispatches instead of the
planned 10, at Sonnet/Opus token ceilings 5–15× pass 1's — an order of magnitude over the
stated budget, discovered only after the (already-expensive, ~65k–140k tokens each) dry-run
stage completed. Per this project's own "state the actual candidate count up front... never
silently scale a pass up mid-run" discipline, that scale-up was not authorized, so **t4 is
excluded from pass 2's real-execution scoring** — a new, pass-2-specific exclusion, distinct
from t1's permanent one. t4's dry-run output is reported above qualitatively (it clearly
shows the same knobs pushing the same directions the wording intends — more explicit
decomposition and more Opus/Sonnet picks under `budget_margin=+2`'s "derived from an explicit
`expected_tokens` estimate" wording) but contributes no scored real-execution data this pass.

candidate, all Haiku tier, `token_ceiling` 1,300–6,000 (10 real dispatches, matching the
originally-stated per-task cost). Scored with `optimizer.score_candidate` and the same
haiku overhead floor pass 1 measured (28,508 tokens):

**All ten land `under_budget_oversized`. `accuracy_rate` is 0.0 for every candidate this
pass** — the metric this whole search optimizes has zero discriminating power on t6 this
round, and the search runs entirely on the `mean_loss` tiebreak.

This is structurally the *same* problem pass 1 named for t1 (a real haiku dispatch's own
fixed overhead is noisy at the hundreds-of-tokens level, which swamps a budget this small),
now showing up on t6 too, for the same underlying reason: a real, single-guard-clause,
single-file edit costs a haiku sub-agent only ~340–1,050 net tokens once the ~28,508-token
floor is subtracted — under half of every `budget_margin` level tested, including the
tightest (`-1`, "padded generously... 2–3×", which should if anything be the LOOSEST). No
knob wording pushes `token_ceiling` low enough to land in the `[0.5, 1.0]` "within_budget"
band against real spend this small, because the floor itself is bigger than the task.

## The one real signal, taken via code, not eyeballed

Running `optimizer.coordinate_ascent_step` over this data (trace in
[`2026-08-21-pass2-ascent-trace.json`](2026-08-21-pass2-ascent-trace.json)):

- **`budget_margin`: 2 → 1.** `budget_margin=+1`'s mean_loss (0.1917) beats the current
  point's (0.2400) and every other tested level. This *reverses* part of pass 1's own
  headline finding — pass 1 called `budget_margin=+2` "the clearest winner," but that result
  was scored on the excl-t1 set (t4+t6 combined), and re-checking the raw records shows t4's
  single row was doing essentially all of that work. With t4 excluded this pass, t6 alone
  mildly prefers `+1` over `+2`, not because `+2` got worse, but because the signal that made
  `+2` look strong is exactly the signal this pass had to exclude.
- **Every other knob: no move.** `effort_tax`, `calibration_aggressiveness`, `calibration_decay`,
  and `pass_b_feedback`'s neighbors were evaluated against the *original* combined point
  (parallel-sweep, the same shape pass 1 used — see "What this pass didn't do" below), and
  none of their scores beat the updated current point once `budget_margin` moved. None of
  them show a real effect at this measurement resolution either way.

Final settings after pass 2: `budget_margin=1, effort_tax=-1, calibration_aggressiveness=1,
calibration_decay=0, pass_b_feedback=1`.

## Why passes 3 and 4 are paused here, not run to satisfy the count

The user's confirmed plan was 4 sequential passes. Running passes 3 and 4 as designed would
mean dispatching more real builds against the same channel that Finding 2 just showed
produces no `accuracy_rate` signal at all on the only task left to measure with. Per this
project's own repeated discipline (state scope before spending, name a structural
measurement gap rather than build around it silently — the same call pass 1 made for t1),
spending another two passes' worth of real-build budget against a channel already shown to
be all-noise-no-signal on its only remaining task is not "confirming the plan," it's ignoring
what the last measurement said. **Passes 3–4 are paused, not abandoned**, pending one of:

1. A redesign of the accuracy measurement itself — e.g. tasks with a real codebase target
   large enough that a genuine implementation costs more than the overhead floor's own noise
   band (which this experiment now knows is on the order of ±1,000 tokens around 28,508 for
   haiku), rather than a synthetic scratch-file stand-in.
2. Multiple repetitions per candidate (this pass ran n=1 per candidate on t6, same as pass 1's
   effective per-cell n) to average down the floor's own variance, at proportionally higher
   cost.
3. Explicit user sign-off to keep spending real-build budget against t6 alone despite Finding
   2, if the mean_loss-only signal is judged useful enough on its own.

## What this pass didn't do

- **Not a true sequential walk.** Like pass 1, every knob's neighbors were evaluated against
  the shared starting point in one round, not re-evaluated after each accepted move — the
  same gap pass 1's own "Lessons" section named. The `budget_margin` move this pass found is
  solid (it's the knob actually walked); the other four knobs' "no move" verdicts are weaker
  than a true sequential pass would give, because they were never re-checked against
  `budget_margin=1`.
- **No repeated draws.** n=1 per candidate on t6, same single-draw-noise caveat pass 1 named.
- **No `citation_ledger.json` entry for SelfBudgeter.** `calibration_decay`'s text lives only
  in tuning-experiment variants (levels 1/2), not in the shipped agent file — per
  `DESIGN.md`'s "Grounding the 5th knob," a ledger entry is only added if/when a future pass
  promotes this knob into a merged diff.

## Known limitations (repeated from `DESIGN.md`, with this pass's actual numbers)

- **Single-draw noise per candidate** — sharper here than pass 1: every t6 candidate's
  "actual" spend (338–1,046 net tokens) is within the same order of magnitude as the floor's
  own apparent variance (28,846–29,554 raw, a ~700-token spread on ostensibly the same
  no-op-adjacent task) — Finding 2 above.
- **Coarse `accuracy_rate` at small n** — total breakdown this pass: n=1 per candidate,
  accuracy_rate pinned at 0.0 for all ten, so this pass's entire result rides on `mean_loss`.
- **A local, not global, optimum** — unchanged from pass 1; more true here given the parallel-
  sweep gap above.
