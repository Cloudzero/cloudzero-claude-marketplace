# Prompt-tuning pass 4 — first `within_budget` result of the whole experiment

Continues from [pass 3](2026-08-22-pass3.md)'s move (`budget_margin=1 → -1`). New current
point: `budget_margin=-1, effort_tax=-1, calibration_aggressiveness=1, calibration_decay=0,
pass_b_feedback=1`. Same 10-candidate shape; three of `budget_margin`'s neighbors this pass
(`0`, `1`, `2`) are **exact-match reuses of pass 3's own candidates** — `budget_margin`'s other
four knobs are unchanged between the two passes, so those three variants were already rendered
and measured. Only the 6 genuinely new candidates (`effort_tax`, `calibration_aggressiveness`,
`calibration_decay`, `pass_b_feedback`'s neighbors, now evaluated with `budget_margin=-1`
fixed instead of pass 3's stale `+1`) needed fresh dry-runs + real builds.

**`effort_tax=+1` lands `within_budget`** — the first `accuracy_rate=1.0` real-execution
result across all four passes of this experiment. `effort_tax=+1`'s wording ("Default to LOW
effort whenever the difficulty score is uncertain") pushed the dry-run's own `token_ceiling`
up to 15,000 (vs. 3,000–8,000 for every other candidate this pass), which happens to land the
real ~12,960-token requirement squarely in the [0.5, 1.0] band.

Read this honestly, not triumphantly: `effort_tax`'s wording change doesn't reduce the real
work — the actual net spend (12,960) is within the same tight cluster (12,500–15,100) every
candidate across passes 3–4 has shown. What moved is the blueprint's own *stated ceiling*,
which happened to land in the right place this time. That's still the metric this whole
experiment optimizes (`token_ceiling` calibration, not real spend reduction) — it's a genuine
win by that metric, but the mechanism is "the wording made the model quote a bigger number,"
not "the wording made the work cheaper."

## The move, taken via code

`optimizer.coordinate_ascent_step`, current = `pass4_current` (accuracy=0.0, mean_loss=0.3377):

- `budget_margin`: no move — all three neighbors (`0`, `1`, `2`) score worse than the current
  `-1` (confirms pass 3's finding holds at this point too, not just in isolation).
- `effort_tax`: **moves `-1 → +1`** — `accuracy_rate` 0.0 → 1.0 beats on the primary criterion
  outright, mean_loss 0.3377 → 0.0000 alongside it. This is the single biggest move of the
  whole four-pass experiment.
- `calibration_aggressiveness`, `calibration_decay`, `pass_b_feedback`: no move — none of
  their neighbors' `accuracy_rate` (all 0.0) beats the now-current `1.0`.

**Final settings, converged for this pass count**: `budget_margin=-1, effort_tax=1,
calibration_aggressiveness=1, calibration_decay=0, pass_b_feedback=1`.

The proposed diff against the shipped agent file is
[`2026-08-22-final-winner.patch`](2026-08-22-final-winner.patch), generated via
`generate_variant.py` — not applied, per this study's own design (a human reviews and merges
it separately). It combines:
- `budget_margin=-1` — pads `token_ceiling` generously (2–3× expected spend) rather than
  precisely.
- `effort_tax=+1` — defaults to LOW effort under difficulty uncertainty.
- `calibration_aggressiveness=1` — the calibration-ledger correction rule from pass 1 (never
  reversed across any pass).
- `calibration_decay=0` (shipped wording, unmodified) — the SelfBudgeter-grounded knob never
  won a move across passes 2–4; see "Known limitations" below.
- `pass_b_feedback=1` — the Pass B corrected-ceiling-number rule from pass 1 (never reversed).

## Was this "4 passes"?

Yes, per the user's confirmed request to continue tuning "if you are seeing improvements"
through pass 4. Passes 1–2 ran against the since-redesigned (structurally broken) t6 target;
passes 3–4 are the first two passes against the fixed measurement and are the ones whose
numbers should actually be trusted. This is disclosed plainly rather than treating all four
passes as one continuous, comparable series — they aren't.

## Known limitations (repeated with this pass's actual numbers)

- **n=1 per candidate, both passes 3 and 4.** The `within_budget` result rode on one real
  dispatch landing at 12,960 net tokens against a 15,000 ceiling — a comfortable margin
  (ratio 0.864, well inside [0.5, 1.0]), but still one draw. Repeating `effort_tax=1` a few
  more times before treating this as a stable win would directly address this project's own
  standing "single-draw noise" caveat.
- **Parallel-sweep, not fully sequential**, same as every prior pass — `calibration_decay`
  and `pass_b_feedback`'s neighbors were evaluated against `pass4_current` (budget_margin=-1,
  effort_tax=-1), not against the effort_tax=+1 point the pass actually ended on. A true
  sequential walk would re-check those two knobs once more at the final point before calling
  it converged; this wasn't done here, so "converged for this pass count" is accurate but not
  "converged" unconditionally.
- **`calibration_decay` has now been tested at three different base points (pass 2: budget_margin=2;
  pass 3/4: budget_margin=-1 then budget_margin=1) and never once won a move.** Genuine
  negative evidence, not an oversight — the SelfBudgeter-grounded knob's wording doesn't
  appear to move this task's real-execution accuracy, at least not on t6's task shape. Worth
  keeping in mind if `calibration_decay` is ever proposed for promotion into the shipped file
  on the strength of its research grounding alone.
