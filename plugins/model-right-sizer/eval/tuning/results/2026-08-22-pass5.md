# Pass 5 — investigating `calibration_decay`'s null result

Scoped investigation, not a full coordinate-ascent sweep: `calibration_decay` never won a
move across passes 2–4 (three different base points). Before accepting "the wording doesn't
help" at face value, this pass (1) diagnoses *why*, using data already collected, and (2)
tests a reworded `calibration_decay=3` built directly from that diagnosis, at the current
winning point (`budget_margin=-1, effort_tax=1, calibration_aggressiveness=1,
pass_b_feedback=1` — the first time `calibration_decay` has been tested combined with the
actual winning `effort_tax`, not a stale earlier point).

## Diagnosis: the knob's precondition never fires in this benchmark

`calibration_decay`'s levels 1–2 are both worded around a **calibration ledger** —
*"tolerance should tighten as more `within_budget` rows accumulate for that shape"* /
*"a calibration ledger with no stated decay rate is under-specified."* Both statements only
have something to act on if a ledger of past observations already exists.

Two pieces of evidence, both already in hand from passes 2–4, no new dispatch needed:

1. **Every dry-run this entire experiment has ever run reports
   `uncertainty_ledger.calibration.ledger_found: false`.** This benchmark dispatches a single,
   fresh sub-agent per candidate with no history — there is never a ledger for the knob's own
   conditional to fire against.
2. **The dry-run rationale text never once engages with the wording.** Across every
   `calibration_decay=1`/`=2` dry-run in passes 2–5, the blueprint's rationale never mentions
   tightening, decay, or a ledger. The model isn't ignoring the instruction — it's correctly
   reading it as inapplicable to a first (and only) observation, which is exactly what the
   wording says should happen absent a ledger.

## The fix tried: `calibration_decay=3`

Reframes the same SelfBudgeter Formula 6 mechanism for the regime this benchmark actually
tests — a first observation, not a repeated one: *"absent a calibration ledger, a task-shape's
first observation is still on the schedule's permissive starting end, not its tight
asymptote... pad `token_ceiling` generously... and only tighten once real `within_budget`
rows for that shape actually exist."* Same curve, correctly identifying which end of it
applies when there's no history yet.

## Result — the fix didn't win, and the apparent tie is probably noise, not signal

| candidate | model picked | budgeted | actual (net) | ratio | class | accuracy | mean_loss |
|---|---|---:|---:|---:|---|---:|---:|
| `pass5_current` (calibration_decay=0) | haiku | 15,000 | 12,960 | 0.864 | `within_budget` | 1.0 | 0.0000 |
| `calibration_decay=1` | **sonnet** | 15,000 | 9,222 | 0.615 | `within_budget` | 1.0 | 0.0000 |
| `calibration_decay=2` | haiku | 12,000 | 12,520 | 1.043 | `over_budget` | 0.0 | 0.0433 |
| `calibration_decay=3` | haiku | 12,000 | 13,209 | 1.101 | `over_budget` | 0.0 | 0.1007 |

`optimizer.coordinate_ascent_step`: **no move.** `calibration_decay=1` ties the current
point's `accuracy_rate` (1.0) and `mean_loss` (0.0), but `select_best`'s own "Less is More"
tiebreak (prefer the candidate closer to the all-zero baseline) keeps `calibration_decay=0` —
correctly, since a tie is not evidence to change the shipped wording.

**Read this honestly, not hopefully**: `calibration_decay=1`'s tie is most plausibly
explained by something unrelated to its wording. Its dry-run picked **Sonnet** this round —
every other `calibration_decay` dry-run across all five passes picked Haiku — and Sonnet's
real net spend on this task (9,222 tokens) happens to be substantially lower than every
haiku run's (12,500–13,300). `calibration_decay`'s text says nothing that would plausibly
cause a model-tier switch; this looks like ordinary LLM sampling variance in the dry-run's own
tier pick, the same kind of noise this whole experiment has been fighting since pass 1, not a
causal effect of the reworded knob. **`calibration_decay=3` — the actual test of this pass's
diagnosis-driven hypothesis — landed worse than doing nothing** (`over_budget`, mean_loss
0.1007 vs. the current point's 0.0000).

## Conclusion

The diagnosis (no calibration ledger ever exists in this benchmark, so ledger-conditioned
wording is structurally inert) is well-evidenced and stands. The proposed fix
(`calibration_decay=3`) does not improve accuracy on this one draw — if anything it's the
worst-scoring candidate tested this pass. `calibration_decay` stays at level 0 (unmodified)
in the current best-known settings. This is genuine negative evidence on a second, deliberately
better-targeted attempt, not just an absence of a win — worth stating plainly rather than
trying a level 4.

**Two ways this could still be resolved, not pursued in this pass**:
1. Repeat `calibration_decay=1` and `=3` a few more times each to separate the model-tier
   sampling noise from any real wording effect — n=1 per candidate is not enough to
   distinguish "ties because Sonnet is cheaper here" from "ties because the wording helped."
2. Accept that `calibration_decay`'s underlying mechanism (tightening across *repeated*
   observations) may not be testable at all by this benchmark's single-dispatch protocol,
   regardless of wording — the same category of structural mismatch as `t1`'s per-item
   budget, just on the measurement-protocol side rather than the task-size side.

Current best-known settings, unchanged from pass 4: `budget_margin=-1, effort_tax=1,
calibration_aggressiveness=1, calibration_decay=0, pass_b_feedback=1`.
