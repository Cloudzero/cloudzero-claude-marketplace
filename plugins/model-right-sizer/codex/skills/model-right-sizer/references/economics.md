## Economic formalization (research-grounded): why effectiveness vs. efficiency is the right split

Before the effort dial, there is the split itself — and it is not an ad hoc rubric. **Token Economics** / *"Token Economics for LLM Agents: A Dual-View Study from Computing and Economics"* (Chen, Chen, He et al. [arXiv 2605.09104](https://arxiv.org/abs/2605.09104), Zhejiang University / Alibaba Cloud) formalizes LLM-agent inference as a **constrained cost-minimization problem** — exactly the shape of every call you make:

- **The master objective (Eq. 3):** `min TC  s.t.  Y ≥ Z` — minimize total cost subject to a quality floor. This *is* your effectiveness-vs-efficiency split, made literal: **effectiveness need is the constraint** (does the pick clear `Y ≥ Z`?), **efficiency pressure is the objective** (minimize `TC`). A blueprint row that can't state what `Z` is hasn't actually specified the constraint it's optimizing under.
- **The cost function (Eq. 2):** `TC = P_k·K + P_m·M + w·L` — capital (`K`, compute/model tier), tokens (`M`, reasoning + tool-call spend), and human labor (`L`, the wage rate `w` pricing your own time), each at its own unit price. This is the same three-way ledger your usage report already itemizes (model tier cost, token/thinking budget, and — via the loop-class/wall-clock lever — the human time a slow agentic loop burns); the paper gives it one closed form instead of three separate lines.
- **The production function (Eq. 1):** `Y = A · [δK^ρ + (1−δ)M^ρ]^(θ/ρ) · L^β · e^ε` is a nested CES (Constant Elasticity of Substitution) form — `K` (capital/model tier) and `M` (tokens) can *substitute* for each other up to a point. **Translate:** this is the formal reason "a `high`-effort mid-tier model can beat a `low`-effort top-tier model" — tokens and model tier are substitutable factors, not a fixed hierarchy. The substitution parameter `ρ` sets how far that goes: `σ = 1/(1−ρ)` (footnote 4) — as `ρ→1`, `σ→∞` and the factors are near-perfect substitutes (throw tokens at a weak model and it's fine); as `ρ→−∞`, `σ→0` and they become **rigidly complementary** — the paper's own name for this boundary is the **"Memory Wall"**: past it, more reasoning tokens on an undersized model buy *nothing*. That is the formal backing for treating a model floor as real rather than negotiable on some task shapes, and for marking an aggressive down-pin `measurement-required` instead of assuming tokens can always compensate.
- **The shadow price of a token is not its sticker price.** Footnote 5 defines it recursively as the scope widens: single-agent `P̃ = P_m + w·τ_inf` (token price *plus* the wage-rate cost of the latency/tool-invocation time it burns) → multi-agent `P̃_comm = P_m + w·τ_sync + ΔC_coord` (adds inter-agent sync latency *and* a coordination-cost term) → ecosystem `P̃_eco = P_m + w·τ_cong + C_comp` (adds congestion + compliance externalities). **Translate:** this is the formal justification for two levers already in this rubric — "latency is a first-class cost on agentic loops" is pricing `w·τ_inf` into the token, and "schema debt is real debt" is pricing `ΔC_coord`: an undefined handoff schema is exactly the coordination-cost term the shadow price says you're paying whether you name it or not.
- **The optimal model/effort mix is where the marginal rate of technical substitution equals the shadow-price ratio** (Figure 5): at the cost-minimizing point `E*`, `MRTS = P̃_ext/P̃_int` — the trade-off between internal reasoning tokens and external tool tokens settles exactly where their price ratio says it should, not before. A pick that over- or under-invests in one relative to the other, at those prices, isn't yet at `E*`.
- **The deterministic-query-layer lever has a literal amortization test**, not just an intuition: the paper's GraphRAG example states a fixed indexing/build investment `I_graph` is justified when `I_graph / Q < ΔY` per query — the one-time cost, amortized over expected query volume `Q`, must undercut the per-query quality/cost delta `ΔY` it buys. Before flagging a `query_shaped` stage as worth a deterministic layer, this is the inequality that pick is actually claiming holds.

None of this changes what you output — it's the formal ground under the rubric you already run, and it's why the two adaptive-reasoning-budget results below target the `M` (token) side of this production function specifically: they tell you *how* `M` should scale with difficulty once this framing has already told you *that* `K`, `M`, and `L` are substitutable factors under a shared budget.

## Adaptive reasoning-budget layers (research-grounded)

Model choice is only half the lever; *how much a chosen model reasons* is the other half, and it should be allocated per-task, not set once. Two results ground how you set the effort dial and the token/thinking budget — cite them when asked why a stage got the effort it did:

1. **Difficulty-adaptive effort — do not reason uniformly.** IBPO / *"Think Smarter, not Harder: Adaptive Reasoning with Inference-Aware Optimization"* ([arXiv 2501.17974](https://arxiv.org/abs/2501.17974)) shows that long-reasoning models default to "single-modal" behavior — the same long chain on every query — and that *learning to match reasoning length to query difficulty* beats it: **+4.14–5.74% absolute MATH500 accuracy at a fixed 2–4× budget, ~2× the accuracy-per-compute of self-consistency.** Translate: score each task's **difficulty** and make the effort dial a *function of difficulty*, not a global default. High effort/thinking only where difficulty earns it; minimal or none on easy, well-specified stages. **Over-thinking an easy stage is a right-sizing failure — the "over-thinking tax" — exactly as much as under-powering a hard one.** This is the analytic case for defaulting effort *down* and spending it deliberately.

2. **Explicit budget + graded adherence — signal the budget, don't just hope.** BudgetThinker / *"Empowering Budget-aware LLM Reasoning with Control Tokens"* ([arXiv 2508.17196](https://arxiv.org/abs/2508.17196), Wen, Wu, Li et al., Tsinghua AIR) makes the budget a **first-class control signal**: it "periodically insert[s] special control tokens during inference to continuously inform the model of its remaining token budget," trained with a **length-aware reward that optimizes accuracy AND budget adherence at once** — and as a result *sustains* accuracy across a range of budgets rather than degrading. Translate: every blueprint row and build unit carries an **explicit token/thinking budget** (not just a model+effort), the sub-agent spawn is *told* that budget so it self-truncates, and **budget adherence is a graded objective** — the usage report scores actual-vs-budgeted spend as its own line, not an afterthought. A stage with no stated budget is under-specified.

Together these sharpen the existing effort lever into a **difficulty → effort → explicit-budget** chain: difficulty sets how hard to think, the budget makes that concrete and enforceable, and adherence is measured after. Neither replaces model choice — they govern the *reasoning spend within* whatever model clears the effectiveness bar.

## Serving-layer lever: speculative decoding (research-grounded)

Model tier and reasoning budget aren't the only dial — *how the chosen model is served* is a third, independent lever, and it is the one place this rubric can buy back latency **without** downgrading effectiveness. Leviathan, Kalman & Matias, *"Fast Inference from Transformers via Speculative Decoding"* ([arXiv 2211.17192](https://arxiv.org/abs/2211.17192), ICML 2023, Google Research) is the grounding result:

- **The mechanism.** A smaller draft model M_q proposes γ candidate tokens; the target model M_p verifies all of them in one parallel pass instead of γ+1 serial ones, with the output distribution provably unchanged (not an approximation). The expected number of tokens produced per pass is E(# generated tokens) = (1−α^(γ+1))/(1−α) (Eq. 1), where α is the draft-model acceptance rate (Definition 3.1) — how often M_p accepts a token M_q already proposed.
- **The payoff.** That gives an expected walltime-improvement factor of (1−α^(γ+1))/((1−α)(γc+1)) (Theorem 3.8), where c is the cost coefficient (Definition 3.7): the ratio of one M_q step's time to one M_p step's time.
- **The gate — does this help at all?** If α > c, there exists a γ with the improvement factor at least (1+α)/(1+c) (Corollary 3.9). Below that gate, no choice of γ helps; this is the `what_flips_it` condition for any blueprint row that proposes this lever.
- **The catch — it always costs more total compute, and the walltime win only cashes out when that compute is otherwise idle.** The expected factor of increase in total arithmetic operations is (1−α)(γĉ+γ+1)/(1−α^(γ+1)) (Theorem 3.11, where ĉ is the analogous per-token-operations ratio) — always ≥ 1 for α < 1. Theorem 3.8's walltime win assumes (Section 3.4) enough spare compute headroom to run those extra operations concurrently for free; the paper states the failure mode directly: "our method is not helpful for configurations where additional computation resources are not available." A high-concurrency, already-batched serving stack — many simultaneous requests already keeping the GPU compute-bound — is exactly that configuration.

**Translate for a blueprint row:** this is a candidate lever only where (a) the effectiveness-need score already requires the strong tier, (b) efficiency pressure is dominated by *interactivity* — a human watching, low concurrency, latency felt directly — the opposite regime from the Batch APIs lever above, and (c) the org controls its own inference stack (self-hosted serving with a configured draft model). It is not a lever available against a closed frontier API whose decode strategy you don't control, and it is the wrong call on a high-throughput batched row even when (a) and (c) hold — that row's serving stack is already compute-bound, so there is no idle headroom left for the free verification pass to spend.

## Agent-to-agent message-schema design (the fourth lever)

Model tier, reasoning budget, and serving-layer choices (above) govern what one agent spends *thinking* and how fast it's served. There is a fourth, independent spend: what one agent hands the *next* agent, at every stage-to-stage seam in a multi-agent chain. A cheap model reading a bloated handoff can cost more tokens than an expensive model reading a tight one — right-sizing the chain means right-sizing both ends of every seam, not just the model at each end.

- **Design the schema, don't let it default to "paste the transcript."** For every handoff — build stage → review stage, finder → verifier, sub-agent → orchestrator, one PromptQL-planning stage → the stage that consumes its result — specify the minimal structured payload the receiving stage actually needs: named fields, types, and an explicit exclusion list ("do not pass: the full transcript, raw retrieved rows, chain-of-thought, tool call logs"). A schema with no exclusion list is under-specified the same way a stage with no token budget is.
- **This applies to PromptQL and non-PromptQL hops alike.** A query-layer stage should hand its consumer the query result plus a compact provenance note (what was asked, what plan ran), not the full row set or its own reasoning about how it got there; an LLM-to-LLM hop should hand structured findings (e.g. `{claim, file, line, confidence}`), not a prose summary the next agent has to re-parse. The lever is the same regardless of what produced the payload: pass the smallest structured fact set that preserves what the next stage must act on, and cite the source rather than re-quoting it.
- **Enforce it as a first-class blueprint deliverable, not an aside.** The work-routing map (below) names a schema for every handoff alongside the tier/effort/budget for every stage — a build unit or blueprint row with tiers assigned but no defined handoff schema is as incomplete as one with no budget. The usage report grades **schema adherence** the same way it grades budget adherence: did the actual handoff match the designed schema, or did it balloon back into free-form prose?
- **Where this saves the most:** fan-outs (one finder's output read by N verifiers — a bloated schema multiplies), long pipelines (schema debt compounds hop-over-hop), and any stage whose consumer is a cheaper model (a small model paying full price to parse a verbose handoff erodes the tier saving you just banked).
